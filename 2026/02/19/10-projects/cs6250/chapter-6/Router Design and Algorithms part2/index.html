    Router Design and Algorithms Part2

    数据包分类（Packet Classification）：为什么我们需要它？

    从一个生活类比开始：邮局分拣

    想象你在一个邮局工作。最简单的分拣方式是：只看信封上的”收件地址”，然后把信扔到对应的邮筒里。这就是传统路由器做的事情——根据目的 IP 地址（destination IP address）进行最长前缀匹配（longest prefix matching），然后转发数据包。

    但现在，邮局的需求变复杂了：

    • 有些信来自被列入黑名单的寄件人，需要直接丢弃
    • 有些是加急快递，需要走专门的快速通道
    • 有些大客户预约了每天固定的运力，需要给他们预留带宽

    这时候，光看”收件地址”就不够了。你还需要看寄件人是谁、信件类型是什么、有没有特殊标记等等。

    在网络世界里，这种”不仅看目的地址，还要看多个字段来决定如何处理数据包”的做法，就叫做数据包分类（Packet Classification）。

    核心问题：为什么传统转发不够用？

    传统转发的工作方式

    传统路由器在转发数据包时，只做一件事：

    1. 取出数据包头部（packet header）中的目的 IP 地址（destination IP address）
    2. 在路由表（routing table）中进行最长前缀匹配（Longest Prefix Matching, LPM）
    3. 找到匹配的条目后，把数据包从对应的出口（output port）转发出去

    这种方式简单高效，但它只关心一个维度——“这个包要去哪里”。

    为什么这不够？

    随着互联网日益复杂，网络需要为流量提供两类保障：

    1. 服务质量保障（Quality of Service, QoS）：比如视频通话的数据包需要低延迟，不能和普通网页浏览的数据包一样排队等待
    2. 安全保障（Security）：比如需要阻止来自某些恶意来源的流量

    要实现这些保障，路由器必须根据多个条件来判断如何处理一个数据包，这些条件可能包括：

    • 源 IP 地址（source IP address）：这个包从哪里来？
    • 目的 IP 地址（destination IP address）：这个包要去哪里？
    • 源端口号（source port）
    • 目的端口号（destination port）
    • 协议类型（protocol type）：是 TCP 还是 UDP？
    • TCP 标志位（TCP flags）：比如 SYN、ACK 等标志

    这种基于多个字段、更精细地处理数据包的机制，就是数据包分类（Packet Classification）。

    在继续之前，请你暂停几秒钟，试着自己想一想：在现实网络中，有哪些场景需要路由器不仅仅看目的地址，而是要看更多信息来决定怎么处理数据包？

    想好了吗？下面我们来看三个经典的应用场景。

    数据包分类的三大经典应用场景

    1. 防火墙（Firewalls）

    是什么？ 防火墙是部署在网络入口和出口处的安全机制，由路由器实现。

    做什么？ 它根据预定义的规则，检查每个经过的数据包，决定是放行还是丢弃。

    为什么需要数据包分类？ 防火墙的规则通常不只看目的地址。比如：

    • “丢弃所有来自 IP 地址 10.0.0.5 的数据包”——需要看源地址
    • “只允许 TCP 端口 80（HTTP）和 443（HTTPS）的流量通过”——需要看协议类型和端口号
    • “阻止所有带有 SYN 标志但没有 ACK 标志的入站连接”——需要看 TCP 标志位

    类比：防火墙就像大楼的保安，不是只看你要去哪个楼层（目的地址），还要看你的身份证（源地址）、你带了什么东西（协议/端口）、你有没有预约（TCP 标志位）。

    2. 资源预留协议（Resource Reservation Protocols）

    是什么？ 这类协议允许网络为特定的流量预先分配带宽等资源。

    典型例子：DiffServ（Differentiated Services，差分服务）。DiffServ 可以在源（source）和目的（destination）之间预留带宽（bandwidth）。

    为什么需要数据包分类？ 要实现资源预留，路由器必须能识别出”哪些数据包属于被预留了资源的那条流”。这需要匹配源地址、目的地址、甚至端口号等多个字段。

    类比：这就像高速公路上的 HOV 车道（高承载车道）。要判断一辆车能不能走 HOV 车道，不能只看它要去哪里，还要看车里坐了几个人（多个条件匹配）。

    3. 基于流量类型的路由（Routing Based on Traffic Type）

    是什么？ 根据流量的具体类型（比如视频、语音、普通数据），选择不同的转发路径。

    为什么需要？ 不同类型的流量对网络的要求不同：

    • 视频和语音是时间敏感型应用（time-sensitive applications），需要低延迟、低抖动
    • 普通文件下载对延迟不敏感，但需要高吞吐量

    通过识别流量类型并选择合适的路径，可以避免时间敏感型应用遭受不必要的延迟。

    类比：这就像医院的分诊台。急诊病人（视频流量）走绿色通道，普通门诊病人（普通数据）走正常排队流程。

    数据包分类问题的直观解法（Straightforward Approaches to Packet Classification）

    0. 先建立背景：什么是数据包分类（Packet Classification）？

    在正式讲三种方法之前，我们必须先搞清楚”数据包分类”到底在解决什么问题，否则后面的一切都是空中楼阁。

    想象你是一栋大楼的保安。每个进出大楼的人（数据包）都带着一些信息：姓名、工牌号、要去的楼层、来自哪个公司等。你手里有一本厚厚的规则手册（rules database），比如：

    • “来自A公司、去5楼的人 → 放行”
    • “来自B公司、去机房的人 → 拒绝”
    • “所有人去1楼大厅 → 放行”

    你的任务就是：对每一个进来的人，翻规则手册，找到最匹配的那条规则，然后执行对应的动作。

    在网络中，路由器/防火墙就是这个保安。数据包的”信息”就是包头字段（header fields），比如源IP地址、目的IP地址、源端口、目的端口、协议类型等。规则手册就是一组分类规则（classification rules）。每条规则定义了”如果包头字段满足某些条件，就执行某个动作（转发、丢弃、标记优先级等）”。

    核心挑战：规则可能有成千上万条，而数据包到达的速度极快（高速链路上每秒数百万个包），我们必须在极短时间内完成匹配。

    1. 方法一：线性搜索（Linear Search）

    1.1 原理

    这是最朴素、最直接的方法。

    做法：拿到一个数据包后，从规则数据库的第一条规则开始，逐条往下比对。每比对一条，就检查这个包是否匹配该规则。同时，始终记录当前找到的”最佳匹配规则”（best-match rule）。遍历完所有规则后，就用那条最佳匹配规则来处理这个包。

    为什么要记录”最佳匹配”而不是”第一个匹配”？因为规则之间可能有重叠。比如：

    • 规则1：”所有去80端口的流量 → 放行”（很宽泛）
    • 规则2：”来自恶意IP且去80端口的流量 → 丢弃”（更具体）

    一个来自恶意IP、去80端口的包同时匹配两条规则，但我们希望用更具体的那条。所以必须全部扫完，找到最佳的。

    1.2 类比

    就像你在一本没有索引的电话簿里找一个人的号码——只能从第一页翻到最后一页。

    1.3 性能分析

    • 如果规则很少（比如几十条），线性搜索完全够用，简单可靠。
    • 但如果规则数据库有成千上万条规则（现实中的企业防火墙很常见），每个包都要逐条扫描，时间开销就变得不可接受（prohibitive）。

    假设有 N 条规则，每条规则的比对需要一次内存访问，那么最坏情况下，分类一个包的时间复杂度是 O(N)。

    1.4 实际应用

    原文指出，防火墙（Firewall）的实现中确实使用线性搜索。这说明在规则数量较少的场景下，线性搜索因为实现简单、不需要额外数据结构，是一个合理的选择。

    2. 方法二：缓存（Caching）

    2.1 原理

    核心思想：如果我们已经对某个数据包做过分类，把结果存起来（缓存），下次遇到相同特征的包时，直接查缓存，不用再搜索规则库。

    这就像你是保安，遇到一个经常来的人，你记住了他的脸和对应的规则，下次他来就不用翻手册了。

    2.2 两个致命问题

    原文明确指出缓存方法有两个问题，我们逐一拆解：

    问题一：缓存未命中（Cache Miss）仍然不可避免

    即使缓存命中率（cache-hit rate）高达 80%-90%，仍然有 10%-20% 的包在缓存中找不到结果。这些”未命中”的包怎么办？还是得回去做完整的搜索（比如线性搜索）。所以缓存并没有消除慢速搜索的需求，只是减少了它的频率。

    问题二：即使命中率很高，平均性能仍然可能很差

    这是一个非常关键的定量分析，原文给出了具体数字，我们来完整推导：

    假设条件：

    • 缓存查找耗时：100 纳秒（nsec），即一次内存访问的时间
    • 规则库有 10,000 条规则
    • 线性搜索耗时：每条规则一次内存访问 → 10,000 × 100 nsec = 1,000,000 nsec = 1 毫秒（msec）
    • 缓存命中率：90%

    计算平均搜索时间：

    Code

    0.1 毫秒看起来不大，但对于高速网络来说，这仍然太慢了。一条 10 Gbps 的链路上，最小包（64字节）的到达间隔大约是 50 纳秒左右。0.1 毫秒 = 100,000 纳秒，远远跟不上线速（line rate）。

    直觉理解

    这里的关键洞察是：缓存未命中的代价太高了。即使未命中只占 10%，但每次未命中的代价是命中的 10,000 倍（1,000,000 / 100），所以未命中的那 10% 主导了整体性能。

    这就像一个餐厅，90% 的订单 1 分钟就能出餐，但 10% 的订单需要 100 分钟。平均等待时间 = 0.9×1 + 0.1×100 = 10.9 分钟，体验依然很差。

    3. 方法三：传递标签（Passing Labels）

    3.1 核心思想

    既然在每个路由器上都做分类太贵，那我们换一个策略：只在网络边缘（edge）做一次分类，然后把分类结果”贴”在数据包上，作为一个标签（label）。后续路径上的所有中间路由器只需要读这个标签，就知道该怎么处理这个包，完全不需要重新做分类。

    这就像机场安检：你在入口安检处被检查一次，然后给你一个登机牌（标签）。之后你在候机厅、登机口、飞机上，工作人员只看你的登机牌，不会再让你重新过安检。

    3.2 MPLS（多协议标签交换，Multiprotocol Label Switching）

    MPLS 是这种”传递标签”思想的典型实现，主要用于流量工程（Traffic Engineering）。

    完整工作流程：

    第一步：在站点 A 和站点 B 之间，预先建立一条标签交换路径（Label-Switched Path, LSP）。这条路径上的每个路由器都知道”看到标签 X 就转发到下一跳 Y”。

    第二步：当流量要从站点 A 发往站点 B 时，站点 A 边缘的路由器对数据包进行完整的分类（比如识别出这是 Web 流量），然后将分类结果映射为一个 MPLS 头部（MPLS header），贴在数据包上。

    第三步：A 和 B 之间的所有中间路由器（intermediate routers）只需要查看 MPLS 标签，根据标签做转发决策。它们完全不需要重新做数据包分类。这大大加快了中间路由器的处理速度。

    3.3 DiffServ（区分服务，Differentiated Services）

    DiffServ 采用了类似的思路，但目标不同——它关注的是服务质量（Quality of Service, QoS）。

    做法：在网络边缘，路由器对数据包进行分类，然后在包头中标记（mark）一个特殊的字段（DSCP，Differentiated Services Code Point），表示这个包应该获得什么级别的服务（比如高优先级、低延迟等）。之后，网络内部的路由器只需要读这个标记，就知道该给这个包什么待遇。

    3.4 传递标签方法的本质

    这种方法并没有让分类本身变快，而是通过架构设计，把分类的工作量从”每个路由器都做”减少到”只在边缘做一次”。这是一种用空间换时间、用预处理换实时计算的策略。

    局限性：这种方法需要网络基础设施的支持（路由器必须理解 MPLS 或 DiffServ），而且只适用于可以预先规划路径或服务等级的场景。对于需要在每个节点独立做分类决策的场景（比如独立的防火墙），这种方法不适用。

    4. 三种方法的对比总结

    方法 原理 优点 缺点
    线性搜索 (Linear Search) 逐条扫描规则库 实现简单 规则多时太慢，O(N)
    缓存 (Caching) 存储之前的分类结果 命中时极快 未命中代价太高，平均性能仍差
    传递标签 (Passing Labels) 边缘分类一次，标签传递 中间节点无需分类 需要基础设施支持，不通用

    这三种方法都是”直观的”（straightforward）解法，各有局限。这也是为什么后续需要研究更高级的算法解法（algorithmic solutions），比如基于 Trie 的方法、决策树方法等。

    5. 费曼自检 Checklist

    Q1: 什么是数据包分类（Packet Classification）问题？它为什么困难？

    answer 数据包分类是指：对于每一个到达的数据包，根据其包头字段（如源/目的IP、端口、协议等），在一组预定义的规则中找到最佳匹配的规则，并执行对应的动作。它困难的原因是：规则可能有成千上万条，而高速链路上数据包到达速度极快，必须在极短时间内完成匹配。

    Q2: 线性搜索为什么要记录”最佳匹配”而不是找到第一个匹配就停下？

    answer 因为规则之间可能有重叠，一个数据包可能同时匹配多条规则。我们需要找到最具体/最优先的那条规则（best-match rule），所以必须遍历完所有规则，始终跟踪当前最佳匹配。

    Q3: 缓存方法的两个问题分别是什么？请用自己的话解释。

    answer 问题一：即使命中率高达 80%-90%，仍有 10%-20% 的包需要回退到完整搜索（如线性搜索），缓存无法消除慢速搜索的需求。问题二：未命中的代价远高于命中的代价（可能差几个数量级），所以即使未命中比例小，它对平均时间的贡献仍然是主导性的。原文例子中，90% 命中率下平均时间仍为 0.1 msec，对高速网络来说太慢。

    Q4: 请手动推导：缓存命中率 90%，缓存查找 100 nsec，线性搜索 10,000 条规则每条 100 nsec，平均搜索时间是多少？

    answer 平均时间 = 0.9 × 100 + 0.1 × (10,000 × 100) = 90 + 100,000 = 100,090 nsec ≈ 0.1 msec。关键洞察：未命中的 10% 贡献了 100,000 nsec，而命中的 90% 只贡献了 90 nsec，未命中完全主导了平均性能。

    Q5: MPLS 的完整工作流程是什么？它如何避免中间路由器重复做分类？

    answer 第一步：在站点 A 和 B 之间预先建立标签交换路径（LSP）。第二步：站点 A 边缘路由器对数据包做完整分类，将结果映射为 MPLS 头部贴在包上。第三步：中间路由器只读 MPLS 标签做转发，不需要重新分类。本质是把分类工作集中在边缘做一次，用标签传递结果。

    Q6: DiffServ 和 MPLS 的思路有什么相似之处？目标有什么不同？

    answer 相似之处：都是在网络边缘做一次分类，然后通过标记/标签传递分类结果，让内部路由器无需重复分类。不同之处：MPLS 主要用于流量工程（Traffic Engineering），控制流量走哪条路径；DiffServ 主要用于服务质量（QoS），标记数据包应获得的服务等级。

    Q7: 为什么说这三种方法都是”直观的”解法，还需要更高级的算法？

    answer 线性搜索在规则多时太慢；缓存无法解决未命中时的高代价问题；传递标签需要特殊基础设施支持且不通用（不适用于独立防火墙等场景）。三种方法都无法在通用场景下高效解决大规模规则库的快速分类问题，因此需要专门的算法（如基于 Trie、决策树等）来实现更高效的分类。

    集合剪枝 Trie 树（Set Pruning Tries）：二维数据包分类

    一、问题背景：为什么需要二维分类？

    1.1 从一维到二维

    在网络中，路由器需要对每一个到来的数据包（packet）做出决策：这个包应该走哪条路？应该被允许还是被丢弃？

    最简单的情况是一维分类（one-dimensional classification）：只看数据包的目的 IP 地址（destination IP address），在一棵前缀 Trie 树中做最长前缀匹配（Longest Prefix Match, LPM），就能找到对应的转发规则。这是你之前学过的经典路由查找。

    但现实中，防火墙（firewall）和服务质量（QoS）策略往往需要同时看两个甚至更多字段。比如：

    • 目的 IP 地址（destination IP）
    • 源 IP 地址（source IP）

    这就变成了二维分类（two-dimensional classification）问题。

    类比：想象你在机场安检。一维分类就像只看你的护照（目的地）来决定你走哪个通道。二维分类则是同时看你的护照（目的地）和你的登机牌（出发地），两个条件一起决定你应该走哪个通道。

    1.2 规则表（Rule Table）

    我们用一张规则表来定义分类策略。每条规则由两个前缀组成：一个匹配目的地址，一个匹配源地址。

    规则 (Rule) 目的地址前缀 (Destination Prefix) 源地址前缀 (Source Prefix)
    $R_1$ $0*$ $10*$
    $R_2$ $0*$ $01*$
    $R_3$ $0*$ $1*$
    $R_4$ $00*$ $1*$
    $R_5$ $00*$ $11*$
    $R_6$ $10*$ $1*$
    $R_7$ $*$（通配符，匹配所有） $00*$

    逐条解读：

    • $R_1$：如果一个数据包的目的地址以 0 开头，并且源地址以 10 开头，就匹配这条规则。
    • $R_2$：目的地址以 0 开头，源地址以 01 开头。
    • $R_3$：目的地址以 0 开头，源地址以 1 开头。
    • $R_4$：目的地址以 00 开头，源地址以 1 开头。
    • $R_5$：目的地址以 00 开头，源地址以 11 开头。
    • $R_6$：目的地址以 10 开头，源地址以 1 开头。
    • $R_7$：目的地址是 *（通配符，任何地址都匹配），源地址以 00 开头。

    这里的 * 表示”后面可以是任意比特”。所以 0* 匹配所有以 0 开头的地址，00* 匹配所有以 00 开头的地址，而单独的 * 匹配一切地址。

    关键观察：一个数据包可能同时匹配多条规则。比如一个目的地址为 001...、源地址为 110... 的包，它同时匹配 $R_3$（目的 0*，源 1*）、$R_4$（目的 00*，源 1*）和 $R_5$（目的 00*，源 11*）。当多条规则匹配时，我们需要选择”代价最低”（lowest-cost）或”优先级最高”的那条规则。

    1.3 核心问题

    问题是：给定一个数据包的（目的 IP，源 IP）二元组，如何快速在规则表中找到匹配的最优规则？

    暴力方法是逐条扫描所有规则，但规则可能有成千上万条，这太慢了。我们需要一种高效的数据结构。

    二、Set Pruning Tries 的核心思想

    2.1 直觉：分而治之

    先想一想：如果你已经会用 Trie 树做一维的最长前缀匹配，那面对二维问题，你会怎么扩展？

    暂停 3 秒，自己想一想……

    一个自然的想法是：

    先用第一个维度（目的地址）缩小范围，再用第二个维度（源地址）精确匹配。

    这就是 Set Pruning Tries 的核心思路：

    1. 先建一棵目的地址 Trie 树（destination trie）。
    2. 在目的地址 Trie 树的每个相关节点上，”挂载”（hang）一棵源地址 Trie 树（source trie）。
    3. 查找时，先在目的地址 Trie 中匹配，找到对应的源地址 Trie，再在源地址 Trie 中做最长前缀匹配。

    类比：想象一个图书馆的分类系统。第一层按”学科”（目的地址）分区，每个学科区域内部再按”作者姓氏”（源地址）排列。你先走到正确的学科区，然后在那个区内找到正确的作者。Set Pruning Tries 就是这种”两层索引”结构。

    2.2 符号约定

    为了方便讨论，我们用 $S_i$ 表示规则 $R_i$ 的源地址前缀（source prefix）。例如：

    • $S_1 = 10*$（来自 $R_1$ 的源地址前缀）
    • $S_2 = 01*$（来自 $R_2$）
    • $S_3 = 1*$（来自 $R_3$）
    • $S_4 = 1*$（来自 $R_4$）
    • $S_5 = 11*$（来自 $R_5$）
    • $S_6 = 1*$（来自 $R_6$）
    • $S_7 = 00*$（来自 $R_7$）

    注意 $S_3$、$S_4$、$S_6$ 的值都是 1*，但它们来自不同的规则，关联着不同的目的地址前缀。

    三、构建 Set Pruning Tries：逐步详解

    3.1 第一步：建立目的地址 Trie 树

    我们先把所有规则的目的地址前缀提取出来：

    • *（来自 $R_7$）
    • 0*（来自 $R_1, R_2, R_3$）
    • 00*（来自 $R_4, R_5$）
    • 10*（来自 $R_6$）

    用这些前缀构建一棵二进制 Trie 树（binary trie）：

    Code
    • 根节点代表前缀 *（空前缀，匹配一切）
    • 从根走 0 到达的节点代表前缀 0*
    • 从根走 0 再走 0 到达的节点代表前缀 00*
    • 从根走 1 再走 0 到达的节点代表前缀 10*

    3.2 第二步：在每个节点挂载源 Trie 树

    这是 Set Pruning Tries 最关键的一步。对于目的地址 Trie 中的每个节点（代表某个目的地址前缀 $D$），我们需要挂载一棵源 Trie 树，这棵源 Trie 树包含所有与 $D$ “兼容”（compatible）的规则的源前缀。

    什么叫”兼容”？ 如果一个数据包的目的地址匹配到了前缀 $D$，那么所有目的地址前缀是 $D$ 的前缀（或等于 $D$）的规则，都有可能匹配这个数据包。

    先想一想：为什么不能只挂载目的地址前缀恰好等于 $D$ 的规则？

    暂停思考……

    答案是：前缀匹配是包含关系。如果一个数据包的目的地址匹配了 00*，那它一定也匹配 0*（因为 0* 是 00* 的前缀），也一定匹配 *（通配符匹配一切）。所以在 00* 这个节点上，我们不仅要考虑目的地址恰好是 00* 的规则，还要考虑目的地址是 0* 和 * 的规则。

    类比：这就像地理上的包含关系。如果你在”北京市海淀区”，那你同时也在”北京市”，也在”中国”。所以”海淀区”这个节点需要继承”北京市”和”中国”层级的所有规则。

    3.3 逐节点分析

    现在我们逐个节点来确定应该挂载哪些源前缀：

    节点：根（代表 *）

    哪些规则的目的地址前缀是 * 的前缀或等于 *？只有 $R_7$（目的地址就是 *）。

    所以根节点挂载的源 Trie 包含：${S_7}$，即 ${00*}$。

    节点：0（代表 0*）

    一个数据包如果目的地址匹配到 0*，那它也匹配 *。所以我们需要包含：

    • 目的地址恰好是 0* 的规则：$R_1, R_2, R_3$ → 源前缀 $S_1=10, S_2=01, S_3=1*$
    • 目的地址是 0* 的祖先前缀的规则（即 *）：$R_7$ → 源前缀 $S_7=00*$

    合计：${S_1, S_2, S_3, S_7}$，即 ${10, 01, 1, 00}$。

    节点：00（代表 00*）

    一个数据包如果目的地址匹配到 00*，那它也匹配 0*，也匹配 *。所以我们需要包含：

    • 目的地址恰好是 00* 的规则：$R_4, R_5$ → 源前缀 $S_4=1, S_5=11$
    • 目的地址是 0* 的规则：$R_1, R_2, R_3$ → 源前缀 $S_1=10, S_2=01, S_3=1*$
    • 目的地址是 * 的规则：$R_7$ → 源前缀 $S_7=00*$

    合计：${S_1, S_2, S_3, S_4, S_5, S_7}$，即 ${10, 01, 1, 1, 11, 00}$。

    注意这里 $S_3=1$ 和 $S_4=1$ 值相同但来自不同规则，在源 Trie 中它们会映射到同一个 Trie 节点，但需要记录两条不同的规则。

    节点：10（代表 10*）

    一个数据包如果目的地址匹配到 10*，那它也匹配 1*（但我们的规则表中没有目的地址恰好是 1* 的规则），也匹配 *。所以：

    • 目的地址恰好是 10* 的规则：$R_6$ → 源前缀 $S_6=1*$
    • 目的地址是 * 的规则：$R_7$ → 源前缀 $S_7=00*$

    合计：${S_6, S_7}$，即 ${1, 00}$。

    Code

    每个挂载的源 Trie 本身也是一棵二进制 Trie 树，用于对源地址做最长前缀匹配。

    四、查找过程（Lookup）

    4.1 算法步骤

    假设来了一个数据包，目的地址为 00110...，源地址为 11010...。

    第一步：在目的地址 Trie 中匹配

    从根开始，逐比特匹配目的地址：

    • 第 1 位是 0 → 走左子树，到达节点 0（匹配前缀 0*）
    • 第 2 位是 0 → 走左子树，到达节点 00（匹配前缀 00*）
    • 第 3 位是 1 → 没有子节点了，停止

    在这个过程中，我们经过了三个有源 Trie 的节点：根（*）、0（0*）、00（00*）。

    第二步：在每个经过的源 Trie 中匹配源地址

    对于每个经过的节点，我们用源地址 11010... 在其挂载的源 Trie 中做最长前缀匹配：

    • 根节点的源 Trie ${S_7=00}$：源地址以 1 开头，不匹配 `00`。无匹配。
    • 节点 0 的源 Trie ${S_1=10, S_2=01, S_3=1, S_7=00}$：源地址 11... 匹配 $S_3=1*$。记录 $R_3$。
    • 节点 00 的源 Trie ${S_1, S_2, S_3, S_4, S_5, S_7}$：源地址 11... 匹配 $S_3=1$、$S_4=1$、$S_5=11$。最长匹配是 $S_5=11$，对应 $R_5$。

    第三步：选择最优规则

    在所有匹配的规则中（$R_3, R_4, R_5$ 等），根据预定义的优先级或代价（cost），选择代价最低的那条。

    但实际上，Set Pruning Tries 有一个优化：因为每个节点的源 Trie 已经包含了所有祖先节点的规则，所以我们只需要在目的地址 Trie 中匹配到的最深节点（最长前缀匹配）的源 Trie 中查找即可。在这个例子中，最深匹配是 00*，所以只需在 00* 的源 Trie 中查找。这正是 Set Pruning 的精髓——通过预先”剪枝”（pruning）并复制规则到子节点，使得查找时只需访问一棵源 Trie。

    4.2 用一句话总结查找

    在目的地址 Trie 中找到最长匹配的节点，然后在该节点挂载的源 Trie 中对源地址做最长前缀匹配，得到最终规则。

    五、关键挑战：源 Trie 中应该存什么？（Pruning 的含义）

    5.1 “剪枝”（Pruning）的含义

    “Set Pruning” 这个名字中的 “pruning”（剪枝）指的是：对于目的地址 Trie 中的每个前缀 $D$，我们把整个规则集”剪枝”为只保留与 $D$ 兼容的规则子集。

    具体来说，对于目的地址前缀 $D$，兼容的规则是指：规则的目的地址前缀是 $D$ 的前缀（prefix of $D$），或者等于 $D$。

    为什么是”$D$ 的前缀”而不是”$D$ 的子串”？ 因为如果一个数据包的目的地址精确匹配到了 $D$，那么所有比 $D$ 更短的、且是 $D$ 前缀的目的地址前缀也一定匹配。

    5.2 以 $D = 00*$ 为例的详细推导

    先想一想：如果我们只在 00* 的源 Trie 中放 $R_4$ 和 $R_5$ 的源前缀（因为只有它们的目的地址恰好是 00*），会出什么问题？

    暂停思考……

    问题是：一个目的地址匹配 00* 的数据包，它的目的地址也一定匹配 0* 和 *。所以 $R_1$（目的 0*，源 10*）、$R_2$（目的 0*，源 01*）、$R_3$（目的 0*，源 1*）、$R_7$（目的 *，源 00*）都可能匹配这个数据包。

    如果我们不把这些规则的源前缀也放进 00* 的源 Trie，我们就会漏掉合法的匹配，导致错误的分类结果。

    所以，00* 的源 Trie 必须包含：

    • $R_4, R_5$ 的源前缀（目的地址恰好是 00*）
    • $R_1, R_2, R_3$ 的源前缀（目的地址是 0*，是 00* 的前缀）
    • $R_7$ 的源前缀（目的地址是 *，是一切前缀的前缀）

    这就是为什么 00* 节点的源 Trie 包含 ${S_1, S_2, S_3, S_4, S_5, S_7}$——总共 6 个源前缀，几乎是全部 7 条规则。

    六、致命缺陷：内存爆炸（Memory Explosion）

    6.1 问题的本质

    你可能已经注意到了：同一个源前缀会被复制到多棵源 Trie 中。

    以 $S_7 = 00$（来自 $R_7$，目的地址为 ``）为例：

    • 根节点的源 Trie 包含 $S_7$ ✓
    • 0* 节点的源 Trie 包含 $S_7$ ✓
    • 00* 节点的源 Trie 包含 $S_7$ ✓
    • 10* 节点的源 Trie 包含 $S_7$ ✓

    $S_7$ 出现在每一棵源 Trie 中！因为 $R_7$ 的目的地址是通配符 *，它与所有目的地址前缀都兼容。

    类似地，$S_1, S_2, S_3$（来自目的地址 0* 的规则）出现在 0* 和 00* 两棵源 Trie 中。

    6.2 最坏情况分析

    假设有 $N$ 条规则，目的地址 Trie 有 $M$ 个节点。在最坏情况下（比如很多规则的目的地址是短前缀或通配符），每条规则的源前缀可能被复制到 $O(M)$ 棵源 Trie 中。总的存储空间可能达到 $O(N \times M)$，远远超过原始规则表的 $O(N)$。

    类比：这就像一个公司的通知系统。如果 CEO 发了一条全公司通知（相当于通配符规则），这条通知需要被复制到每个部门的公告板上、每个小组的公告板上、每个人的收件箱里。一条通知变成了成百上千份副本。

    6.3 数字直觉

    在我们的小例子中，7 条规则产生了 $4 + 4 + 6 + 2 = 16$ 个源前缀条目（分布在 4 棵源 Trie 中），而原始规则表只有 7 条。膨胀率约为 2.3 倍。

    在真实的路由器中，规则可能有数十万条，目的地址 Trie 可能有数万个节点，膨胀率可能达到几十倍甚至上百倍，导致内存需求不可接受。

    6.4 权衡总结

    方面 Set Pruning Tries 的表现
    查找速度 快——只需遍历两棵 Trie（目的 + 源），时间复杂度 $O(W)$，$W$ 为地址位宽

    更新难度 中等——插入/删除一条规则可能需要更新多棵源 Trie

    这就是 Set Pruning Tries 的核心矛盾：用空间换时间。它通过预先复制规则来加速查找，但代价是内存爆炸。

    Reducing Memory Using Backtracking

    The set pruning approach has a high cost in memory to reduce time.

    The opposite approach is to pay in time to reduce memory.

    Let’s assume a destination prefix D. The backtracking approach has each destination prefix D point to a source trie that stores the rules whose destination field is exactly D. The search algorithm then performs a “backtracking” search on the source tries associated with all ancestors of D.

    So first, the algorithm goes through the destination trie and finds the longest destination prefix D matching the header. Then it works its way back up the destination trie and searches the source trie associated with every ancestor prefix of D that points to a nonempty source trie.

    Since each rule is stored exactly once, the memory requirements are lower than the previous scheme. But, the lookup cost for backtracking is worse than for set-pruning tries.

    Grid of Tries（网格字典树）—— 数据包分类中的高效查找方法

    一、前置知识回顾：为什么需要二维匹配？

    在网络中，路由器收到一个数据包（packet）后，需要根据规则表（rule table）决定如何处理它。最简单的情况是只看一个字段，比如目的地址（destination address）。但在实际的数据包分类（packet classification）中，我们往往需要同时匹配两个甚至多个字段，比如：

    • 目的地址前缀（destination prefix）
    • 源地址前缀（source prefix）

    这就是所谓的二维匹配问题（two-dimensional classification problem）。

    类比理解：想象你在图书馆找书。一维匹配就像只按”作者姓氏”查找；二维匹配则是同时按”作者姓氏”和”出版年份”查找。你需要两个条件都满足，才算找到目标。

    二、Trie（字典树）是什么？——核心数据结构

    在深入之前，必须理解 Trie（字典树/前缀树）。

    Trie 是一种树形数据结构，专门用来做前缀匹配（prefix matching）。每个节点代表前缀的一个比特（bit），从根节点到某个节点的路径就构成了一个前缀。

    三、已有的两种方案及其问题

    在 Grid of Tries 出现之前，已经有两种解决二维匹配的方案。理解它们的缺陷，是理解 Grid of Tries 价值的关键。

    方案 A：Set Pruning（集合剪枝）

    核心思路：

    1. 先对目的地址（destination）建一棵 Trie。
    2. 对于目的地址 Trie 中的每一个前缀节点，都单独建一棵完整的源地址（source）Trie。

    查找过程：先在目的地址 Trie 中找到最长匹配的前缀，然后直接在该节点挂载的源地址 Trie 中查找源地址的最长匹配。

    优点：查找速度快，一次目的地址匹配 + 一次源地址匹配就完成了。

    致命缺点：内存开销巨大。因为每个目的地址前缀节点都要维护一棵独立的源地址 Trie，很多规则会被重复存储在多棵源地址 Trie 中。

    类比：就像图书馆为每个作者都复制了一整套按年份排列的书架。虽然找书很快，但你需要巨大的空间来放这些重复的书架。

    方案 B：Backtracking（回溯）

    核心思路：

    1. 同样先对目的地址建一棵 Trie。
    2. 但源地址 Trie 不再为每个目的前缀都复制一份，而是只在有规则的目的前缀节点上挂载对应的源地址 Trie（共享，不重复）。

    查找过程：

    1. 先在目的地址 Trie 中找到最长前缀匹配，比如匹配到了 D = 00*。
    2. 在 D = 00* 对应的源地址 Trie 中查找源地址。
    3. 如果在这棵源地址 Trie 中没找到匹配——关键来了——需要回溯（backtrack）到目的地址 Trie 中 00* 的父节点（即 0*），再去 0* 对应的源地址 Trie 中查找。
    4. 如果还是没找到，继续回溯到更短的目的前缀，重复这个过程。

    优点：内存开销小，因为源地址 Trie 不重复。

    致命缺点：时间开销大。每次回溯都意味着要重新遍历一棵源地址 Trie，最坏情况下可能要回溯很多次。

    类比：图书馆只有一套书架，但如果你在”作者 = Smith, J.”的书架上没找到 2020 年的书，你就得退回去看”作者 = Smith”的书架，再没有就退回”作者 = S”的书架……每次退回都要从头翻一遍。

    四、Grid of Tries（网格字典树）——核心方案

    4.1 核心思想：用预计算（precomputation）消除回溯

    Grid of Tries 的本质是对 Backtracking 方案的优化。它保留了 Backtracking 的内存优势（源地址 Trie 不重复），但通过预计算（precomputation）一种叫做 switch pointer（切换指针）的结构，彻底消除了回溯过程中的浪费。

    关键机制：

    在每棵源地址 Trie 中，当某个节点是一个”失败点”（failure point）——即沿着源地址继续匹配时走不下去了——我们预先计算一个 switch pointer。这个 switch pointer 直接指向下一棵可能包含匹配规则的源地址 Trie 中的对应节点。

    类比：还是图书馆的例子。这次，在”Smith, J.”书架上 2020 年的位置，如果没有书，我们贴了一个便签条，上面写着”请直接去 Smith 书架的 2020 年位置看”。你不需要退回去重新找书架，直接跟着便签条跳过去就行了。这个便签条就是 switch pointer。

    4.2 Switch Pointer 的含义

    Switch pointer 的标签（label）表示的是：当你沿着源地址 Trie 走到这个失败点时，你正在匹配的源地址的下一个比特是什么。指针指向的目标是：在目的地址 Trie 中更短的某个祖先前缀所对应的源地址 Trie 中，与当前匹配进度对应的节点。

    换句话说，switch pointer 帮你”跳过”了两个步骤：

    1. 回溯到目的地址 Trie 的祖先节点（不需要了）
    2. 从头遍历那个祖先节点的源地址 Trie（不需要了）

    你直接跳到了那棵源地址 Trie 中你应该继续匹配的位置。

    4.3 完整查找流程

    1. 在目的地址 Trie 中找到最长前缀匹配 D。
    2. 进入 D 对应的源地址 Trie，开始匹配源地址。
    3. 如果匹配成功，记录当前最佳匹配规则。
    4. 如果匹配失败（走到了失败点），不回溯，而是沿着 switch pointer 跳转到下一棵源地址 Trie 的对应位置。
    5. 在新位置继续匹配源地址。
    6. 重复步骤 3-5，直到没有更多的 switch pointer 可以跟随。
    7. 返回记录的最佳匹配规则。

    在整个过程中，我们始终维护一个”当前最佳源地址匹配”（current best source match）。每次跳转后，如果新位置有更好的匹配，就更新它。

    重要细节：switch pointer 的跳转会跳过那些源字段比我们当前最佳源匹配更短的源地址 Trie。这是因为我们已经有了一个更长的匹配，更短的不可能更优，所以可以安全跳过。

    五、具体例子详解

    原文给出了一个例子，让我们一步步走完整个过程。

    查找目标：目的地址 = 001，源地址 = 001

    第 1 步：目的地址 Trie 匹配

    在目的地址 Trie 中查找 001。假设 Trie 中存在前缀 0*、00* 等，最长前缀匹配结果是 D = 00。

    （注意：001 的前两位是 00，如果 Trie 中没有 001 这个目的前缀，但有 00，那么最长匹配就是 00。）

    第 2 步：进入 D = 00 的源地址 Trie

    在 00 对应的源地址 Trie 中查找源地址 001。

    结果：查找失败。这棵源地址 Trie 中没有能匹配 001 的规则。

    第 3 步：跟随 Switch Pointer

    在失败点处，有一个 switch pointer，标签为 0（表示我们正在匹配源地址的某个比特位为 0 的分支）。这个指针指向节点 x。

    节点 x 位于目的地址 Trie 中某个更短的祖先前缀（比如 0*）所对应的源地址 Trie 中。

    第 4 步：在节点 x 继续匹配

    在节点 x 处继续匹配源地址 001。

    结果：再次失败。

    第 5 步：再次跟随 Switch Pointer

    在节点 x 的失败点处，又有一个 switch pointer，指向节点 y。

    第 6 步：在节点 y 处终止

    到达节点 y 后，算法终止。返回在整个过程中记录的最佳匹配规则。

    对比 Backtracking 的过程

    如果用 Backtracking 方案：

    1. 在 D = 00 的源 Trie 中查找 001 → 失败
    2. 回溯到 D = 0，从头在 0 的源 Trie 中查找 001 → 可能失败
    3. 回溯到 D = *（根），从头在根的源 Trie 中查找 001
    4. ……

    每次回溯都要从源 Trie 的根节点重新开始遍历，浪费了之前已经匹配过的比特信息。

    而 Grid of Tries 通过 switch pointer，直接跳到了正确的位置，跳过了重复的匹配步骤。

    八、费曼自检 Checklist

    用以下问题检验你是否真正理解了 Grid of Tries。如果你能用自己的话向一个完全不懂的人解释清楚每一个问题，说明你真的懂了。

    1. 二维数据包分类问题是什么？为什么比一维匹配更难？

    answer 二维数据包分类需要同时匹配数据包的两个字段（如目的地址前缀和源地址前缀），找到两个字段都匹配的规则。比一维难是因为你不能只在一个维度上做最长前缀匹配就结束——目的地址的最长匹配对应的规则，其源地址字段未必匹配当前数据包的源地址，所以可能需要检查多个目的前缀对应的源地址规则。

    2. Set Pruning 方案的核心思路是什么？它的主要缺点是什么？

    answer Set Pruning 为目的地址 Trie 中的每一个前缀节点都构建一棵独立的、完整的源地址 Trie。查找时先匹配目的地址，再在对应的源 Trie 中匹配源地址。主要缺点是内存开销巨大，因为同一条规则可能被复制到多棵源地址 Trie 中，造成大量冗余存储。

    3. Backtracking 方案的核心思路是什么？它的主要缺点是什么？

    answer Backtracking 只在有规则的目的前缀节点上挂载对应的源地址 Trie（不重复复制）。查找时先找目的地址最长匹配，在其源 Trie 中查找源地址；如果失败，回溯到目的 Trie 的上一级祖先前缀，再从头搜索那个祖先的源 Trie。主要缺点是时间开销大，因为每次回溯都要重新从源 Trie 根节点开始遍历，之前已匹配的比特信息被浪费了。

    4. Grid of Tries 中的 switch pointer 是什么？它解决了什么问题？

    answer Switch pointer 是在源地址 Trie 的失败点（即无法继续匹配的节点）上预先计算好的指针。它直接指向下一棵可能包含匹配规则的源地址 Trie 中的对应位置。它解决的问题是：消除 Backtracking 方案中的回溯开销。不需要退回目的 Trie 的祖先节点再从头遍历源 Trie，而是一步跳到正确位置继续匹配。

    5. 请用自己的话描述 Grid of Tries 的完整查找流程。

    answer (1) 在目的地址 Trie 中找到最长前缀匹配 D。(2) 进入 D 对应的源地址 Trie，开始匹配源地址。(3) 如果匹配成功，记录为当前最佳匹配。(4) 如果匹配失败，不回溯，而是沿着该失败点的 switch pointer 跳转到另一棵源 Trie 的对应节点。(5) 在新节点继续匹配源地址，如果有更好的匹配就更新最佳记录。(6) 重复 (4)-(5) 直到没有更多 switch pointer。(7) 返回最佳匹配规则。

    6. 为什么 switch pointer 跳转时可以安全地跳过某些源地址 Trie？

    answer 因为在跳转过程中，我们维护着"当前最佳源地址匹配"。如果某棵源 Trie 中的源字段比我们已经找到的最佳源匹配更短，那它不可能提供更优的匹配结果，所以可以安全跳过。Switch pointer 的预计算已经考虑了这一点，直接指向下一个有可能提供更长/更优匹配的源 Trie。

    7. Grid of Tries 相比 Set Pruning 和 Backtracking，在时间和空间上的权衡是怎样的？

    answer Grid of Tries 的内存开销接近 Backtracking（源 Trie 不重复，只多了 switch pointer 的存储），远低于 Set Pruning。时间开销接近 Set Pruning（通过 switch pointer 跳转避免了回溯），远低于 Backtracking。它是时间和空间之间的一个优秀折中方案。
