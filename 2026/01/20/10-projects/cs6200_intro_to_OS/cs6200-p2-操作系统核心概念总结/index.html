操作系统导论 (Introduction to Operating Systems)

第一部分：课程概述与操作系统的基本定义

1.1 课程预览 (Lesson Preview)

欢迎来到操作系统的入门课程。在这一讲中，我们将从宏观的视角来认识操作系统，建立起对操作系统的整体理解框架。

本节课将涵盖以下几个核心问题：

首先，我们将解答”什么是操作系统”这个根本性问题，并探讨操作系统在计算机系统中所扮演的角色。

其次，我们会深入了解操作系统的关键组件(key components)、设计原则(design principles)以及组织结构(organizational structures)。

在后续的课程中，我们将对本节提到的各种术语和机制进行更加深入的讲解。但现在，让我们先建立一个基础性的认识。

用最简单的话来说，操作系统是一个对底层硬件系统进行抽象(abstract)和仲裁(arbitrate)的软件。

这里有两个关键词需要理解：

  • 抽象(Abstract)：意味着简化硬件的实际样貌，让应用程序不需要了解硬件的复杂细节
  • 仲裁(Arbitrate)：意味着管理、监督和控制硬件的使用

在整个课程中，我们会看到操作系统为计算机系统中各种类型的硬件组件提供了大量的抽象和仲裁机制。

1.2 视觉隐喻：玩具店经理 (Visual Metaphor: Toy Shop Manager)

为了帮助你更直观地理解操作系统的本质，我们用一个生动的比喻来说明：操作系统就像一个玩具店的经理(Toy Shop Manager)。

让我们来看看玩具店经理和操作系统之间的相似之处：

1.2.1 指导运营资源 (Directing Operational Resources)

玩具店经理的职责：

  • 管理员工，指导他们的工作方向
  • 负责调度(scheduling)、分配(allocating)和分发(distributing)店内资源
  • 决定哪些员工处理哪些订单，使用哪些工具
  • 分配零件和工具等资源

操作系统的对应职责：

  • 控制硬件的使用，包括CPU、内存(Memory)、外围设备(Peripheral Devices)如磁盘、网卡等
  • 决定如何将这些资源分配给各个应用程序

1.2.2 执行工作策略 (Enforcing Working Policies)

玩具店经理的职责：

  • 执行有关公平性(fairness)、安全性(safety)、清洁(clean-up)等方面的政策
  • 决定不同订单的工人如何共享资源（如共享零件和工具）
  • 制定工人完成订单后的清理规则

操作系统的对应职责：

  • 执行关于资源使用的策略
  • 控制对共享资源的公平访问(fair access)
  • 设置资源限制(limits)，如每个进程可以打开的最大文件数
  • 设定阈值，触发内存管理守护进程(memory management daemons)的运行

1.2.3 缓解复杂任务的难度 (Mitigating Difficulty of Complex Tasks)

玩具店经理的职责：

  • 优化和简化整个玩具店的运营
  • 没有经理的话，员工可能不知道如何协调工作、分配任务

操作系统的对应职责：

  • 简化应用程序所看到的底层硬件视图
  • 应用程序通过系统调用(System Calls)与操作系统交互
  • 操作系统代为处理那些复杂的任务

1.3 什么是操作系统？(What Is an Operating System?)

现在让我们正式探讨操作系统的定义和角色。

1.3.1 计算机系统的组成

一个计算机系统由多种硬件组件构成：

  1. 处理器/CPU (Processing Elements/CPUs)

    • 现代CPU通常包含多个核心(cores)
    • 一个CPU可能有不止一个处理单元

  2. 内存 (Memory)

  3. 网络设备 (Network Interconnects)

    • 以太网端口(Ethernet port)
    • WiFi网卡(WiFi card)

  4. 图形处理卡 (Graphics Processing Cards)

    • 如GPU (Graphics Processing Unit)

  5. 存储设备 (Storage Devices)

    • 硬盘(Hard Disks)
    • 固态硬盘(SSDs)
    • 闪存设备(Flash Devices)，如USB驱动器

除了某些特定的嵌入式平台或传感器，这些硬件组件通常会被多个应用程序共同使用。比如在你的笔记本电脑上，可能同时运行着浏览器、文本编辑器、Skype等多个应用。在数据中心的服务器上，也会同时运行Web服务器、数据库或计算密集型模拟程序。

1.3.2 操作系统的位置与角色

操作系统是位于复杂硬件和各种应用程序之间的系统软件层(Layer of Systems Software)。

虽然不存在一个正式的、统一的操作系统定义，但我们可以通过理解其角色和必须提供的功能来认识它。

角色一：隐藏硬件复杂性 (Hiding Hardware Complexity)

操作系统对应用程序和开发者隐藏底层硬件的复杂性。

示例1 - 存储抽象：

  • 你不需要在保存程序输出时关心磁盘扇区(disk sectors)或块(blocks)
  • 操作系统隐藏了各种存储设备（硬盘、SSD、USB闪存）的复杂性
  • 它提供了更高层次的文件(File)抽象
  • 你只需执行读(read)和写(write)操作

示例2 - 网络抽象：

  • 作为Web服务器，你不需要考虑如何组装通信所需的比特和数据包
  • 操作系统提供了套接字(Socket)这个高层抽象
  • 你只需通过套接字发送(send)和接收(receive)数据

角色二：管理硬件资源 (Managing Hardware Resources)

操作系统代表正在执行的应用程序管理底层硬件：

  • 决定应用程序使用多少资源、使用哪些资源
  • 为应用程序分配内存(allocates memory)
  • 将应用程序调度(schedules)到CPU上执行
  • 控制应用程序对各种设备的访问
  • 负责所有类型的资源分配(resource allocation)和资源管理(resource management)任务

角色三：提供隔离与保护 (Providing Isolation and Protection)

当多个应用程序在同一硬件上运行时，操作系统必须：

  • 确保每个应用程序都能取得适当的进展
  • 防止应用程序相互伤害
  • 为不同应用程序分配不同的物理内存区域
  • 确保（除非明确需要）应用程序不会访问彼此的内存

这一点从保护(Protection)角度很重要——防止读取他人数据；从隔离(Isolation)角度也很重要——防止覆盖他人内存。

值得注意的是，即使是传统上被视为嵌入式平台的移动手机，现在也需要这些机制。想想看，你的智能手机上同时运行着多少应用程序？浏览器、Skype、Facebook，还有最基本的电话功能。

1.4 操作系统的正式定义 (Operating System Definition)

总结以上讨论，我们可以给出操作系统的定义：

操作系统是位于应用程序和硬件之间的系统软件层(Layer of Systems Software)。

它具有以下特征：

  1. 拥有访问底层硬件并操纵其状态的特权(Privileges)

    • 与之相反，应用程序软件不允许这样做

  2. 隐藏硬件复杂性(Hide Hardware Complexity)

    • 代表一个或多个应用程序管理硬件

  3. 遵循预定义的策略(Predefined Policies)

    • 按照某些策略进行资源管理

  4. 确保隔离与保护(Isolation and Protection)

    • 确保应用程序彼此隔离和保护

第二部分：操作系统组件与设计

2.1 操作系统组件测验 (Operating System Components Quiz)

让我们通过一个思考练习来加深理解：以下哪些可能是操作系统的组件？

选项 是否属于OS组件 原因
文件编辑器(File Editor) ❌ 否 用户直接与之交互，不直接参与硬件管理
文件系统(File System) ✅ 是 直接负责隐藏硬件复杂性，提供比”磁盘存储块”更简单直观的”文件”抽象
设备驱动程序(Device Driver) ✅ 是 直接负责做出关于硬件设备使用的决策
高速缓存(Cache Memory) ❌ 否 虽然OS和应用程序利用缓存提高性能，但OS并不直接管理缓存——这是硬件自己管理的
网页浏览器(Web Browser) ❌ 否 与文件编辑器一样，是用户交互的应用程序，不直接控制底层硬件
调度器(Scheduler) ✅ 是 负责在共享平台的所有应用程序之间分配对处理器(CPU)的访问权

2.2 抽象与仲裁测验 (Abstraction or Arbitration Quiz)

我们说操作系统”抽象”和”仲裁”计算机系统的使用。让我们判断以下示例属于哪一类：

功能 类型 解释
在多个进程之间分配内存 仲裁(Arbitration) 操作系统管理内存并决定多个进程如何共享
支持不同类型的扬声器 抽象(Abstraction) 提供通用接口，可以插入不同的扬声器设备；设备驱动程序封装了具体硬件的知识
可互换地访问硬盘或SSD 抽象(Abstraction) 使用存储抽象，操作系统可以在底层使用不同类型的设备，而对应用程序隐藏这些差异

2.3 操作系统示例 (Operating System Examples)

不同的操作系统针对不同的运行环境而设计。让我们了解一些主要的操作系统：

2.3.1 桌面/服务器操作系统

  1. Microsoft Windows

    • 自1980年代初期就广为人知
    • 广泛用于个人电脑

  2. UNIX系操作系统(UNIX-based Operating Systems)

    • 起源于1960年代末贝尔实验室(Bell Labs)

    • Mac OS X

    • 苹果设备的操作系统
    • 基于UNIX BSD内核扩展

    • BSD = Berkeley System Distribution of Unix（伯克利系统发行版）

    • Linux

    • 非常流行的类UNIX系统
    • 开源(Open Sourced)
    • 与许多流行的软件库捆绑
    • 有多个版本：Ubuntu、CentOS等

2.3.2 嵌入式操作系统

由于智能手机、平板电脑等用户设备的激增，嵌入式操作系统近年来快速发展：

  1. Android

    • 嵌入式Linux的一种形式
    • 运行在各种移动设备上
    • 版本有有趣的名字，如Ice Cream Sandwich、KitKat

  2. iOS

    • 苹果专有的操作系统
    • 用于iPhone和iPad等设备

  3. Symbian 及其他选择

本课程将主要关注Linux操作系统，大多数深入的示例将基于Linux系统。

2.4 操作系统元素 (OS Elements)

为了实现其目标，操作系统支持若干高层抽象(Abstractions)，以及在这些抽象之上运行的关键机制(Mechanisms)。

2.4.1 抽象 (Abstractions)

与应用程序执行相关的抽象：

  • 进程(Process)：代表正在执行的应用程序
  • 线程(Thread)：程序执行的基本单位

与硬件资源相关的抽象：

  • 文件(File)：对应存储设备（如磁盘）
  • 套接字(Socket)：对应网卡
  • 内存页(Memory Page)：对应实际内存

2.4.2 机制 (Mechanisms)

操作系统提供机制来操作这些抽象：

  • 创建(Create)：启动一个应用程序开始执行
  • 调度(Schedule)：将应用程序安排到CPU上运行
  • 打开(Open)：获取对特定设备或硬件组件的访问
  • 写入(Write)：更新资源的状态
  • 分配(Allocate)：确保特定应用程序可以访问该资源

2.4.3 策略 (Policies)

操作系统还集成了特定的策略，决定如何使用这些机制来管理底层硬件：

  • 控制一个进程可以访问的最大套接字数
  • 决定哪些数据将从物理内存中移除
  • 基于算法（如最近最少使用LRU）管理资源

2.5 操作系统元素示例：内存管理 (OS Elements Example: Memory Management)

让我们通过内存管理的例子来理解抽象、机制和策略的关系。

2.5.1 抽象：内存页 (Memory Page)

操作系统使用内存页(Memory Page)作为抽象：

  • 对应某个固定大小的可寻址内存区域
  • 例如：4KB大小

2.5.2 机制

操作系统集成了若干机制来操作内存页：

  1. 分配(Allocate)：在DRAM中分配该页
  2. 映射(Map)：将该页映射到进程的地址空间
    • 允许进程访问对应该页内容的实际物理内存

随着时间推移，这个页可能：

  • 在物理内存中的不同位置之间移动
  • 有时甚至被存储到磁盘上（如果需要为其他内容腾出物理内存空间）

2.5.3 策略：最近最少使用 (Least Recently Used, LRU)

由于从内存访问数据比从磁盘访问快得多，操作系统需要策略来决定页面内容应该存放在哪里。

LRU策略：

  • 在一段时间内最近最少使用的页面将不再保留在物理内存中
  • 这些页面会被复制到磁盘上（称为交换/Swapping）

策略背后的逻辑：

  • 长时间未被访问的页面可能不那么重要
  • 它们很可能在近期也不会被使用
  • 因此可以将它们移到磁盘上
  • 而频繁访问的页面保留在内存中，因为它们更可能被继续使用

2.6 操作系统设计原则 (OS Design Principles)

在设计操作系统时，有一些重要的指导原则：

2.6.1 机制与策略分离 (Separation of Mechanism and Policy)

核心思想：在操作系统中纳入灵活的机制，这些机制可以支持一系列不同的策略。

以内存管理为例，有用的策略可能包括：

  • 最近最少使用(Least Recently Used, LRU)
  • 最不经常使用(Least Frequently Used, LFU)
  • 完全随机(Completely Random)

为了支持这些策略，操作系统需要某种机制来跟踪内存位置被访问的频率或时间。这样，无论选择哪种策略，都可以在同一机制框架内实现。

为什么需要分离？ 因为在不同的设置中，不同的策略更有意义。

2.6.2 针对常见情况优化 (Optimize for the Common Case)

核心思想：我们需要理解操作系统将如何被使用，才能确定什么是”常见情况”。

需要考虑的问题包括：

  • 硬件环境：

    • 将在什么样的机器上运行？
    • 有多少处理器？
    • 有多少内存？
    • 有什么类型的设备？

  • 用户行为：

    • 用户在这台机器上通常做什么？
    • 会执行什么应用程序？
    • 工作负载的特性是什么？

基于对常见情况的理解，选择合适的策略，并利用操作系统支持的机制和抽象来实现它。

第三部分：用户/内核边界与系统调用

3.1 操作系统保护边界 (OS Protection Boundary)

为了实现控制和管理硬件资源的角色，操作系统必须拥有特殊权限(Special Privileges)来直接访问硬件。

3.1.1 两种执行模式

计算机平台至少区分两种模式：

  1. 内核模式(Kernel Mode) - 特权模式

    • 操作系统在此模式下运行
    • 可以直接访问硬件

  2. 用户模式(User Mode) - 非特权模式

    • 应用程序在此模式下运行
    • 不能直接访问硬件

3.1.2 硬件支持

在用户级别和内核级别之间的切换由硬件支持：

  • 特权位(Privilege Bit)：当处于内核模式时，CPU中的一个特殊位被设置

    • 如果设置了这个位，任何直接操纵硬件的指令都被允许执行
    • 当处于用户模式时，这个位未设置，尝试执行特权操作的指令将被禁止

  • 陷阱(Trap)：当用户模式下的应用程序尝试执行特权操作时

    • 应用程序被中断
    • 硬件将控制权切换到操作系统的特定位置
    • 操作系统检查引发陷阱的原因
    • 验证是否应该授予访问权限，或者终止进程（如果它试图执行非法操作）

3.1.3 应用程序与操作系统的交互方式

  1. 系统调用接口(System Call Interface)

    • 操作系统导出一组操作，应用程序可以显式调用
    • 请求操作系统代表它们执行某些服务和特权访问
    • 例如：open（访问文件）、send（通过套接字发送）、malloc（分配内存）

  2. 信号(Signals)

    • 操作系统向应用程序传递通知的机制

3.2 系统调用流程 (System Call Flowchart)

让我们追踪一次系统调用过程中控制和数据的交换：

步骤1：用户进程执行

假设我们当前在一个正在执行的用户进程中。

步骤2：发起系统调用

因为用户进程需要某些硬件访问，它发起一个系统调用。

步骤3：切换到内核模式

  • 控制权传递给操作系统（在特权模式下）
  • 这涉及：
    • 将执行上下文从用户进程更改为OS内核
    • 传递必要的参数
    • 跳转到内核内存中对应该系统调用的指令序列

步骤4：操作系统执行操作

操作系统以特权模式运行，被允许执行系统调用指定的任何操作。

步骤5：返回结果

系统调用完成后：

  • 将结果和控制权返回给调用进程
  • 这涉及：
    • 将执行上下文从内核模式更改回用户模式
    • 将任何参数传回用户地址空间
    • 跳转到用户进程中发起系统调用的确切位置

重要说明：整个过程涉及上下文切换、参数传递和内存跳转，这不是一个廉价的操作。

发起系统调用的步骤

  1. 写入参数：应用程序必须将参数写入
  2. 保存数据：在预定义的位置保存所有相关数据
  3. 使用系统调用号：用特定的系统调用号发起实际的系统调用

预定义位置是必要的，这样操作系统内核可以根据系统调用号确定：

  • 应该获取多少个参数
  • 这些参数在哪里

参数可以直接在用户程序和操作系统之间传递，也可以通过指定地址间接传递。

在同步模式(Synchronous Mode)下，进程会等待直到系统调用完成。（异步系统调用将在后续课程讨论）

3.3 跨越操作系统边界的代价 (Crossing the OS Boundary)

用户/内核转换是应用程序执行过程中的必要步骤：

  • 应用程序可能需要访问某些类型的硬件
  • 可能需要请求更改分配给它们的硬件资源

只有操作系统（内核）被允许执行这些类型的操作。

3.3.1 性能开销

尽管硬件提供支持，执行这些转换仍然需要许多指令：

时间成本示例：

  • 在运行Linux的2GHz机器上
  • 一次用户/内核转换可能需要50到100纳秒
  • 这是实际的时间开销

3.3.2 缓存影响

另一个问题是这些转换对硬件缓存(Hardware Cache)使用的影响：

背景：

  • 访问缓存大约需要几个周期
  • 访问内存可能需要数百个周期
  • 应用程序性能高度依赖于使用硬件缓存的能力

问题：

  • 当我们执行系统调用或进入操作系统时
  • 操作系统在执行过程中可能会将其需要的内容加载到缓存中
  • 这会替换转换之前缓存中的应用程序内容
  • 应用程序将无法从缓存中访问其数据，必须转到内存

总结：用户/内核转换代价不菲，需要谨慎设计以减少不必要的转换。

3.4 操作系统服务 (OS Services)

操作系统通过导出一系列服务为应用程序提供对底层硬件的访问。

3.4.1 基本服务类型

与硬件组件直接相关的服务：

  • 调度组件(Scheduling Component)：控制对CPU的访问
  • 内存管理器(Memory Manager)：将物理内存分配给一个或多个共同运行的应用程序，确保它们不会覆盖彼此的内存访问
  • 块设备驱动程序(Block Device Driver)：负责访问块设备（如磁盘）

与高层抽象相关的服务：

  • 文件系统(File System)：几乎所有操作系统都支持的有用抽象

3.4.2 服务类别总结

操作系统需要整合多种服务来提供有用的功能：

  • 进程管理(Process Management)
  • 文件管理(File Management)
  • 设备管理(Device Management)
  • 等等

3.4.3 系统调用示例

操作系统通过系统调用使所有这些服务可用。以下是Windows和Unix中一些系统调用的对比：

功能类别 Windows Unix
进程控制 CreateProcess(), ExitProcess(), WaitForSingleObject() fork(), exit(), wait()
文件操作 CreateFile(), ReadFile(), WriteFile() open(), read(), write()
设备操作 SetConsoleMode(), ReadConsole() ioctl(), read(), write()

尽管是两个非常不同的操作系统，它们提供的系统调用类型和围绕这些系统调用的抽象非常相似——进程控制、创建进程、退出进程、等待对象、创建文件等。

3.5 系统调用测验 (System Calls Quiz)

在64位Linux操作系统上，以下功能使用哪个系统调用？

功能 系统调用
向进程发送信号 kill
设置进程的组标识 setgid (64位系统；16位或32位系统有setgid16、setgid32变体)
挂载文件系统 mount
读/写系统参数 sysctl (系统控制)

第四部分：操作系统组织结构

4.1 单体式操作系统 (Monolithic OS)

历史上，操作系统采用单体设计(Monolithic Design)。

4.1.1 特点

在单体式操作系统中：

  • 任何应用程序可能需要的每种可能服务
  • 任何类型的硬件可能需要的所有功能
  • 都已经是操作系统的一部分

示例：

  • 可能包含多个文件系统
  • 一个针对顺序工作负载优化（顺序读写文件）
  • 另一个针对随机I/O优化（常见于数据库场景，每个操作可能随机访问文件的任何部分）

4.1.2 优点

  • 一切都包含在操作系统中
  • 抽象、所有服务都同时打包
  • 存在编译时优化(Compile-time Optimizations)的可能性

4.1.3 缺点

  • 状态太多、代码太多
  • 难以维护、调试和升级
  • 体积大导致内存需求高
  • 可能影响应用程序能够观察到的性能

4.2 模块化操作系统 (Modular OS)

当今更常见的方法是模块化方法(Modular Approach)，Linux操作系统就采用这种设计。

4.2.1 特点

  • 有一些基本服务和API已经是操作系统的一部分
  • 更重要的是，一切都可以作为模块(Module)添加
  • 可以轻松定制操作系统使用哪个文件系统或调度器

4.2.2 工作原理

  • 操作系统指定某些接口(Interfaces)
  • 任何模块必须实现这些接口才能成为操作系统的一部分
  • 根据工作负载，可以动态(Dynamically)安装以适当方式实现接口的模块

示例：

  • 如果是数据库应用程序，运行针对随机文件访问优化的文件系统
  • 如果是其他类型的计算，运行针对顺序访问优化的文件系统
  • 可以在操作系统中动态安装新模块

4.2.3 优点

  • 更易维护和升级
  • 更小的代码基础
  • 资源消耗更少：为应用程序留下更多资源（更多内存）
  • 可能带来更好的性能

4.2.4 缺点

  • 模块化虽然有利于可维护性
  • 但需要通过接口规范才能进入特定服务的实现
  • 这可能减少一些优化机会
  • 可能对性能有一些影响（通常不显著）
  • 模块可能来自完全不同的代码库，可能是bug的来源

总体而言，这种方法相比单体方法有显著改进，是当今更常用的方法。

4.3 微内核 (Microkernel)

另一种操作系统设计是微内核(Microkernel)。

4.3.1 特点

微内核在操作系统级别只需要最基本的原语：

内核级别包含的内容：

  • 表示正在执行的应用程序
  • 其地址空间
  • 其上下文（线程/Thread）
  • 进程间通信(Inter-Process Communication, IPC)机制

在用户级别运行的内容：

  • 所有其他软件组件
  • 应用程序（如数据库）
  • 传统上认为是操作系统组件的软件（如文件系统、设备驱动程序）

由于这种组织方式，微内核需要大量的进程间交互。

4.3.2 优点

  • 非常小
  • 不仅可能带来更低的开销和更好的性能
  • 更容易验证和测试代码行为是否正确
  • 在某些对操作系统正确行为特别关键的环境中很有价值
    • 嵌入式设备
    • 某些控制系统

4.3.3 缺点

  • 可移植性存疑：通常针对底层硬件高度专门化和定制
  • 可能有更多针对不同平台的一次性版本
  • 难以找到通用软件组件，导致软件复杂性
  • 进程之间频繁交互意味着频繁的用户/内核切换，这可能代价高昂

4.4 Linux和Mac OS架构 (Linux and Mac OS Architectures)

让我们看看两个流行操作系统的具体架构：

4.4.1 Linux架构

从底层到顶层：

  1. 硬件(Hardware)：最底层

  2. Linux内核(Linux Kernel)

    • 抽象和管理硬件
    • 支持许多抽象和相关机制
    • 由几个逻辑组件组成：
    • I/O管理
    • 内存管理
    • 进程管理
    • 这些组件有明确定义的功能和接口
    • 每个组件可以独立修改或替换（这使Linux的模块化方法成为可能）

  3. 标准库(Standard Libraries)

    • 如实现系统调用接口的库

  4. 实用程序(Utility Programs)

    • 使用户和开发者更容易与操作系统交互

  5. 用户开发的应用程序(User-Developed Applications)：最顶层

4.4.2 Mac OS X架构

Apple的Mac OS X操作系统使用不同的组织方式：

核心：Mach微内核

  • 实现关键原语：
    • 内存管理
    • 线程调度
    • 进程间通信机制（包括RPC）

BSD组件

  • 通过BSD命令行界面提供Unix互操作性
  • POSIX API支持
  • 网络I/O

应用环境

  • 所有应用环境位于这一层之上

底层模块

  • 驱动程序开发环境
  • 可动态加载到内核的内核模块

在本课程中，我们回答了一个重要问题：什么是操作系统？

核心要点回顾

  1. 操作系统的重要性

    • 帮助抽象和仲裁底层硬件系统的使用

  2. 实现方式

    • 依靠抽象(Abstractions)：如进程和线程
    • 依靠机制(Mechanisms)：允许操作这些抽象
    • 依靠策略(Policies)：指定如何修改这些抽象

  3. 系统调用接口(System Call Interface)

    • 允许应用程序与操作系统交互

  4. 组织结构选择

    • 单体式(Monolithic)
    • 模块化(Modular)
    • 微内核(Microkernel)

  5. 具体示例

    • Windows、Linux、Mac OS的系统调用接口
    • Linux和Mac OS的组织结构
